最近在给 [vue-lynx](https://github.com/Huxpro/vue-lynx)（我把 Vue 3 移植到 [Lynx](https://lynxjs.org) 上的自定义渲染器）修 bug 时，撞上了一个诡异的现象：页面渲染一切正常，数据也在流动，但所有路由转场永远停在半路——`await nextTick()` 之后的代码，一行都没有执行过。

追这个 bug 的过程，最后把我引向了一个比它大得多的问题：**框架应该向用户承诺「时间」吗？**

## 一、永远等不到的回执

交代一下背景。Lynx 是双线程架构：你的 Vue 代码跑在 Background Thread（BG）上，操作的只是一棵内存里的影子树；真正的原生元素活在 Main Thread（MT）上。BG 把变更打包成一批 ops，通过 `callLepusMethod('vuePatchUpdate', ops, callback)` **异步**地寄过线程边界。

标准 Vue 的 `nextTick()` 只需要等调度器 flush——因为 DOM 变更是同步的，flush 完 DOM 就真的更新完了，用户可以放心测量布局。但在 vue-lynx 里，flush 完成只意味着 ops「已寄出」。如果 `nextTick` 在这里就 resolve，用户接着查询元素就会扑空。所以 vue-lynx 的 `nextTick` 多等一程：把 `callLepusMethod` 的回调当作回执（ack），等主线程真正应用完再兑现。

而这个 bug 的真相是：我们测试用的那台 source build 的 Explorer，`vuePatchUpdate` 被成功地应用了，**但回调从来没有被调用过**。回执永远不来，promise 永远 pending，转场永远卡死。

修法看起来很简单：加一个 50ms 的兜底 timer，等不到回执就自己 resolve。但 code review 立刻指出了问题——无条件的兜底，等于**拿所有引擎上的正确性去换个别引擎上的活性（liveness）**：健康引擎应用一个大批次超过 50ms 时（低端设备首屏很常见），timer 会抢先 resolve，用户又会查询到尚未物化的元素，而且这比卡死难排查得多。最终落地的是一个锁存（latch）：

```ts
// 一旦观察到引擎回过一次真实回执，就永久信任它，不再挂兜底 timer
app?.callLepusMethod?.('vuePatchUpdate', { data }, () => {
  engineAckObserved = true;  // 健康引擎从此回到严格保证
  ack.resolve();
});
```

回头看这条复杂度链，每一层都是被现实逼出来的：

```text
异步线程边界      →  需要回执，保住 nextTick 的语义
引擎不回执        →  需要兜底 timer，保住活性
timer 误伤健康引擎 →  需要 latch，只对坏引擎降级
```

写完这段代码之后，一个问题开始萦绕不去：ReactLynx 每天在生产环境里跑，**它怎么没被这个引擎缺陷咬到？**

## 二、React 从未签过这份合同

去上游 [lynx-stack](https://github.com/lynx-family/lynx-stack) 里翻 ReactLynx 的源码，答案让我愣了一下。同一个回调就在那里——ReactLynx 发 patch 也走 `callLepusMethod`：

```js
// @lynx-js/react — lifecycle/patch/commit.js
lynx.getNativeApp().callLepusMethod(LifecycleConstant.patchUpdate, obj, () => {
  const commitTask = globalCommitTaskMap.get(commitTaskId);
  if (commitTask) {
    commitTask();  // 延迟回收已移除的 snapshot 实例
    globalCommitTaskMap.delete(commitTaskId);
  }
});
```

但这个回调只做一件事：清理。它不兑现任何用户可见的 promise。整个 ReactLynx runtime 里没有 `nextTick`、没有 `waitForFlush`、没有任何「等主线程应用完」的公开 API。

于是同一个引擎缺陷砸在两个框架上，后果天差地别：在 ReactLynx 里，是一次无人察觉的延迟回收；在 vue-lynx 里，是用户可见的死锁。**区别不在实现，在契约——React 不是解决了这个问题，而是从未签过这份合同。**

## 三、等时间，还是占位置

为什么 React 敢不签？这要回到两个框架的状态模型。

Vue 的响应式基于可变数据（mutation）：`count.value++` 是同步的命令式写入，DOM 效果却被批到 microtask 里。**写入同步、生效异步**，中间这条时间缝隙用户是感知得到的，框架必须给个交代。`nextTick` 就是那个交代——它本质上是把宿主的 event loop 直接暴露给了用户：「我保证，这个 microtask 之后，你的修改已经落在 DOM 上」。在浏览器里，这个承诺几乎免费：DOM 变更本来就是同步的，框架只需要在自己的 watcher 队列排干之后放行。

React 从第一天起就把 `setState` 定义成「**请求**一次重渲染」而不是「修改状态」——state is a snapshot。API 从没承诺过「什么时候生效」，所以也不欠用户一个时间性的答案。React 给的是**位置性**的答案：不告诉你「何时刷完」，而是提供一些保证站在「已提交」这个位置上的钩子——`ref` 回调、`useLayoutEffect`、`useEffect`。你不能 `await` 到那个时刻，但你可以把代码**放置**在那个时刻。

这不是洁癖，而是为调度器保留自由度的深思熟虑。如果 React 承诺了「`await` 之后宿主树一定反映你的更新」，后来的一切都做不成：跨事件的 automatic batching、可中断可重启的并发渲染、transition 的优先级车道——在并发模型里，一次更新可能被打断、重放、被更高优先级超越，甚至**不存在一个良定义的「after」**。时间性的 API 一旦发布，就会被 Hyrum's Law 锁死：总有用户代码依赖「microtask 后一切就绪」，调度器从此再也不能变。React 把调度视为核心竞争力（Fiber 的全部意义），代价就是绝不出售 timing——唯一的例外 `flushSync`，被刻意起了个吓人的名字放在文档的角落里。

而这份克制换来的最大红利是**可移植性**。React Native 和 Lynx 是同构问题：JS 线程与 UI 线程之间隔着一座异步的桥。因为 React 从没承诺过「何时上屏」，同一套心智模型搬到 RN 上几乎零破损——测量布局走异步的 measure 回调，和 DOM 版的心智一致。Vue 的 `nextTick` 契约在浏览器上几乎免费，但搬到异步双线程上，就要**在最贵的环境里兑现最强的承诺**。这就是那张账单。React 通过从不签合同，躲掉了大部分账期——「几乎」和「大部分」这两个限定词，下一节展开。

## 四、当「位置」也过不了桥

写到这里，好像「占位置」全是优点。但位置性 API 有一个隐藏前提：**那个位置必须真的存在于你的线程上。**

`useLayoutEffect` 的承诺是「DOM 已更新、浏览器尚未绘制」——站在这个位置上，你可以同步测量布局、再同步改一次样式，用户看不到中间帧。React 官方的 Tooltip 例子就靠它：先渲染在默认位置，测量，发现放不下，翻到另一侧，而这一切发生在一次绘制之前。

这个承诺在浏览器里成立，是因为 layout 和 JavaScript 住在同一根线程上，`getBoundingClientRect()` 可以强制同步排版。而在 pre-Fabric 的 React Native 上，这个位置根本不存在：`useLayoutEffect` 确实在 commit 后同步执行了，但此刻它身处 JS 线程——真正的视图还在异步桥的另一头排队，Yoga 还没跑，`measure()` 只能给你一个异步回调。于是「测量、再定位」必然横跨两帧，tooltip 闪一下，是那个年代 RN 开发者的集体记忆。**位置性 API 的时刻表是照着同步宿主排的；桥一异步，时刻表作废。**这也是 Fabric 重写渲染器的卖点之一：C++ 共享的 Shadow Tree 加上 JSI 同步调用，让「在 `useLayoutEffect` 里同步测量、赶在这一帧显示前再渲染一次」重新成为可能——React 花了一整代架构，才把这个「位置」在异步宿主上重新造出来。

Lynx 给了另一个方向的答案。它不把「布局刚完成」这个时刻搬到 BG 线程来，而是**把你的代码搬到时刻所在的线程去**：MTS（Main Thread Script）允许把一小段函数标记为 `'main thread'`，直接在主线程上响应 [`main-thread:bindlayoutchange`](https://lynxjs.org/react/lifecycle.html)——布局结果就在手边，同步读、同步改，一帧之内完成。所以 ReactLynx 干脆宣布不支持 `useLayoutEffect`（所有生命周期都在 BG 线程异步执行），官方文档把 React 那个 Tooltip 例子原样重写成了 MTS 版：

```jsx
<view
  main-thread:bindlayoutchange={(e) => {
    'main thread';
    // 布局刚刚完成——这里就是「那个位置」，只是它在主线程上
    measureAndReposition(e);
  }}
/>
```

（pre-Fabric 时代的 RN 社区其实早就发明了同款解法——Reanimated 的 worklet 就是把 JS 函数搬到 UI 线程执行，Lynx 的 MTS 正是这一思路的体系化。）

于是那张对比图上其实有三格，而不是两格：

- **等时间（Vue）**：让时刻穿过桥来找你的代码——桥必须给回执，于是有了 ack 和 latch；
- **占位置（React）**：把代码放在时刻的槽位上——槽位必须在你的线程上存在，于是有了 Fabric；
- **搬代码（MTS / worklet）**：干脆把代码送到时刻所在的线程——代价是这段代码离开了你的组件世界，闭包、状态、能 import 什么，全部要重新立规矩。

第三格也不免费：worklet 是一段被序列化后传送过桥的孤岛，它看得见布局，却摸不到你的 store。但它揭示了这场讨论的底层不变量——**「时刻」只诞生在布局发生的那根线程上。你可以等它的信使（ack），可以订它的座位（effect），也可以亲自搬过去住（worklet），但没有任何框架魔法能让同一个时刻同时存在于两根线程上。**

## 五、没有免费的一边

说到这里，必须替 Vue 说句公道话：它的选择同样自洽，而非「没抽象好」。

Vue 的血统里有 jQuery 时代的渐进增强——「改完就测」的命令式互操作是一等公民，template ref 拿到的就是裸元素。而且细粒度响应式让「flush 之后」这个时刻**良定义且便宜**：watcher 队列在一个 microtask 里排干，确实存在一个确定的「after」可以卖。Vue 卖了这个承诺，因为在它的模型里，它卖得起。

React 的做法也远非免费——复杂度只是换了个地方付账：`useEffect` 与 `useLayoutEffect` 的时序困惑、「为什么我测到的布局是旧的」、ref 回调的心智负担，以及那个不得不存在的 `flushSync`。**一边是框架在内部消化时序（vue-lynx 里那一百行 flush.ts），一边是把时序困惑分摊给每一个用户。复杂度不会消失，只会转移。**

## 尾声

给 Vue 的用户和实现者留一个观察：如果有一天 Vue 走向可中断的并发渲染，`nextTick` 那个「确定的 after」会先于一切成为障碍——到时候大概也得走 React 的老路，引导用户从「等时间」迁移到「占位置」。也许再过几年，`nextTick` 会像今天的 `flushSync` 一样，顶着一个劝退的名字活在文档的角落里。

而对我自己，这次最大的收获是换了一副眼镜：**评价一个 API，不只看它给了用户什么能力，还要看它替框架签下了什么合同。**有些合同在签订的那天几乎免费，利息却要在十年后的另一个宿主环境里才开始计——

`nextTick` 的账单，是我在 Lynx 上替 Vue 付的。
