项目、演讲与它们之间的横轴

Works 只有一根轴（时间）和一种上下文（role → identity，rail 画出来的那条）。现实是一棵树加几条横边。这页先把关系拆清楚，再给五个方向，其中三个做成了可以点的原型，都用的是 log.json 里的真数据。最后是对比矩阵和我的倾向。

0三种关系被压成了一种

现在的 log 里，commit 之间只有两种结构：排序（时间）和归属（attachedTo / tenure 推断出的 role，rail 把它画出来）。但描述的现实至少有这样一棵树：

identity  <jsx@fb.com>  <@bytedance>
 └─ role  SWE @ Meta · Architect @ ByteDance   (tenure, team)
     └─ project / family      React Compiler · Hermes · Lynx
         ├─ release / sub-project    Lynx open source · lynx-ui · ReactLynx
         └─ evidence                 talk · post · press · repo
             └─ edition              EN / 中文 · 重讲 · 续篇

树里每一层之间是一种不同的关系。把它们分开命名，后面每个方向的取舍就清楚了：

关系例子现在PR 249git 里的对应物

同一件作品的另一个 dateline		Two Threads 的 EN/中文；Lynx 首发的 D2 / React Summit / WAD 重讲；世界观 → 前端已死各自一行squash：成员 id 列表 + relations[PATCH v2] re-roll、cherry-pick

纵向太长的压力主要来自第三行：Lynx 是会持续发布的家族，每个 release 带着仓库、演讲、博客，而现在唯一能承载它们的单元是 talk commit。前两行是"已经发生的重复"，第三行是"会持续增长的结构"。一个方向解决哪几行，是判断它的第一把尺子。

ASquash + Project context（PR 249 现状）

两个机制：squash 把 peers 印成一行（header 只说共同点，band 里每个成员说自己的），projects[] 让 talk 像引用 role 一样引用 project（mark / peek / light / fields 四个 register）。

PR 249 预览的 HEAD 章节。HEAD 从现在的 15 行压到 11 行。

我认可的部分：不改写数据，成员保留 hash，per-locale 的因子化很严谨，"context 像 role 一样有四个 register"这个类比是对的。疑虑都是结构性的：

  1. 成本花在了最不增长的那一行上。squash 是第三个顶层集合，带 relations 表和一个因子化算法（log-squash.ts 420 行 + squash-band.tsx 483 行 + 编辑器面板），只解决 edition-of。part-of（Lynx 家族）没有碰，而那才是纵向会持续变长的原因。
  2. 五个 squash 里有两个不是 peers。lynx-open-source 和 china-react 都需要作者补 title 和 description，恰恰说明缺的是一个真正的 commit 来承载这个时刻。按 PR 自己的定义（"a squash is for peers"），它们不该是 squash，是 milestone。
  3. squash 行不再是一个 commit。header 没有 hash（lead 的 hash 只出现在 caption 里），anchor、peek、embed 都要为"一行不是一个 commit"开特例。
  4. 项目行还留在起点。Lynx Framework 在 2023 年那头，它的九个 talk 在上面一屏。context 靠 mark 和跨行 connector 补，行越多越弱。

BThreads：一个指针，最新的 edition 顶起整条线

只处理 edition-of，而且只加一个字段：editionOf: <commitId>，可选 relation 标签。没有 group 实体，lead 是推导出来的。像邮件列表或论坛：thread 的位置由最新一条决定（"被顶上来"），header 是 canonical 那条（原版，或者当前 locale 的那一版），其它 edition 折成标题下面的一行 ↳ 2 editions，点开是每个 edition 的封面和 venue。

HEAD2023 – Present
// commit 上加一个指针，不加集合
{ "id": "see-conf-2025-two-threads",
  "editionOf": "react-universe-2025-two-threads",
  "relation": { "en": "Chinese edition", "zh": "中文版" } }

// header 的选法（推导，不用作者写）：当前 locale 有 edition 就用它，否则用原版
// 行的位置：thread 里最新的 date；日期栏印区间 `Jun – Jul 2025`

好在哪

  • 每一行仍然是一个 commit，hash、peek、anchor 一律不用特例。
  • 数据形状是 git 自己的：(cherry picked from …)、[PATCH v2]，读者一看就懂。
  • 编辑器只需要一个 picker；没有因子化，没有 per-locale 共同字段。
  • 续篇（世界观 → 前端已死）、重讲、翻译用同一个字段，靠 relation 区分。

代价

  • 只解决 edition-of。Lynx 家族的增长还是一行一个 talk。
  • 没有 lead 的 peers（三个 2022 的认可）放不进来。我的看法：它们本来就不是 edition，是一个 milestone 的证据，该归 C 或 D。
  • header 用"当前 locale 的那一版"时，EN 页和中文页 thread 的 hash 不同，分享链接要落到成员 hash 上。

CBranches：项目是一条 branch，行停在它的 tip

把 git log --graph --first-parent 搬过来。每个 project 是一条 lane；关于它的 talk / post / press 是 lane 上的 commit；子项目（lynx-ui）是从 lane 上再分出去的 lane；同时关于两个项目的 talk（Two Threads）是有两个 parent 的 merge。项目行坐在它最近一次活动的位置（tip），而不是起点，所以 Lynx Framework 在 HEAD 顶上，日期栏仍然是 2023 – Present。默认 --first-parent：主线只印项目行加一句 ⎇ 11 commits on lynx；点开才展开 lane。lane 里的 edition 用 B 的 thread 折叠。release 是 lane 上的一个 tag: 装饰，和章节的 HEAD pill 同一套。

HEAD2023 – Present
REACT2017 – 2022同一机制在 React 章节

// PR 的 projects[] 换个更中性的名字，目标可以是任何 commit，于是天然成 DAG
{ "id": "react-advanced-2025-lynx-ui", "about": ["lynx-ui"] }
{ "id": "lynx-ui", "type": "project", "about": ["lynx-framework"], "date": "2025-11" }
{ "id": "react-universe-2025-two-threads", "about": ["lynx-framework", "react-core"] }  // merge

// 项目行的位置：有 lane 的项目按 lane 上最新一条排（tip），日期栏照旧印区间
// 折叠是 form 的一部分：covers 折、feed 展、index 只印计数；?type=talk 时 lane 解散，talk 各自成行

好在哪

  • 三种关系一个机制：about、part-of、merge 都是 parent 指针；role 的 rail 和 project 的 lane 是同一种东西的两层。
  • 直接回答 Lynx 的增长：新 release、新 talk 只让 lane 变长，主线不变。HEAD 折叠后 5 行。
  • 每一行仍是 commit；Meta 时期 Hermes / React Core 两个 team 各有一条 lane，identity 不用拆。
  • 词汇是这个站已经在用的：HEAD、hash、--pretty=fuller，再加 --first-parent 和 tag: 并不突兀。

代价

  • 默认把 2026 的 talk 折在一个 2023 起头的行下面。tip 排序和 ⎇ 11 commits · latest Jul 2026 这行是补偿，但"页面是一条时间线"的直觉被动了一点。
  • 跨章节的 merge（Two Threads → 2021 的 React Compiler）画不出 lane，只能退回 mark。
  • 手机上 lane 是缩进；两层以内可读，三层就挤了。
  • lane 内部还需要 B 来折 edition，所以它是 C+B，不是单独一个。

DReleases：换掉行的单位，talk 变成 release 的证据

不动布局，动内容的单位。在 Lynx 时期，一行是一个 milestone（开源、lynx-ui、下一次大版本），关于它的 talk / 博客 / 仓库是这一行的 attachment。media strip 已经会印封面，所以 talk 直接成了 strip 里的封面，caption 印 venue 和它自己的 hash。talk 仍是 commit（可寻址，?type=talk 时各自成行），只是默认折进它的 milestone。这正是你说的"用发布时的 talk 顶替子项目"的反转：让 release 成为 commit，让 talk 回到证据的位置。

HEAD2023 – Present
// 作者新写两个 commit；talk 用 about 指回去，present 说"我是证据，默认折进去"
{ "id": "lynx-open-source", "type": "project", "date": "2025-03",
  "title": { "en": "Lynx goes open source", "zh": "Lynx 开源" }, "about": ["lynx-framework"] }
{ "id": "d2-2025-lynx", "about": ["lynx-open-source"], "present": "evidence" }

好在哪

  • PR 里两个"不是 peers 的 squash"在这里是诚实的 commit，有 hash，有自己的 prose。
  • 增长的单位是 release：以后每次发布加一行，不是加 N 行 talk。
  • 不加新的渲染机制，strip、caption、sheet 都是现成的。

代价

  • 要作者写 milestone commit。不是每个 talk 都有对应的 release（Two Threads 就没有），硬造会失真。
  • 不处理 edition-of，单独用时压缩有限（HEAD 15 → 13）；要和 B 配。
  • talk 默认从主线消失，"演讲者"这个身份在默认视图里变弱，靠 ?type=talk 找回。

ETrailers + filter：只标注，不改版式

兜底方案。about[] 和 editionOf 只作为 --pretty=fuller 块里的 trailer 印出来（Project: / Edition-of:），meta line 上留 PR 那个稀疏的 mark，再给 URL 加一个 ?about=lynx 过滤。压缩交给读者：想看 Lynx 就过滤，想短就 index form。诚实、便宜，但默认页面一行不会少。它是 B / C / D 任一方向的数据层，所以不单独做原型。

→我的倾向，和要你定的几件事

C 作机制，B 补 edition，D 作内容层面的决定。两个指针字段（about[]、editionOf），零个新集合。project 是 branch，talk 是 branch 上的 commit，edition 是 thread，release 是值得单独一个 commit 的时候才写一个 commit（它自然就是 lane 上的一个 tag）。PR 249 里四个 register 的思路保留给跨章节的引用（Two Threads → React Compiler），因为那里画不出 lane。

理由：这是唯一一个把成本花在会增长的那一行（part-of）上的方向，并且它把 role 的 rail 和 project 的 lane 统一成一种东西，而不是再加一种。

关于 Meta 时期的 identity

现在的做法（一个 identity，project 上挂 team 副标题）我认为是对的，不建议拆成多个 role：rail 画不了重叠的 tenure，而 Hermes 和 React Core 在时间上确实重叠。在 C 里，team 自然成为 lane 的属性（PLR @ Meta 那条、React Core team @ Meta 那条），谈论"我在哪个 team"就是谈论"哪条 lane"，identity 保持一个。

要你定的

  1. 项目行停在 tip 还是起点？C 的压缩依赖 tip。如果你觉得"Lynx Framework 出现在 2026 顶上"违反直觉，替代是留在起点、lane 向上生长（git 的 branch 图其实就是这样画的），代价是折叠后主线读起来是倒的。
  2. thread 的 header 用原版还是当前 locale 的版本？影响 EN / 中文两页的 hash 是否一致。
  3. 默认折叠到哪一层？我倾向 covers form 折 lane、feed 展开、index 只印 ⎇ 11 commits 计数。
  4. Two Threads 这类没有 release 的 talk 要不要硬造 milestone？我倾向不造，让它作为 lane 上的普通 commit + thread。
  5. PR 249 怎么处理？projects[] / short / 四个 register / Attachment origin 这几块可以直接换名沿用；squash 集合和 band 我建议不合入，用 B 的 thread 替代。
