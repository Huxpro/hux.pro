# 天空

天气壁纸：一片 iOS 锁屏风格的动态天空（太阳、月亮、云、雨、雪、雾、闪电、星星），跟随访客所在地的真实天气和太阳、月亮的真实位置，雨和雪沿着设备自身的重力方向落下。这一页讲它是怎么画出来的。它的输入从哪里来，见 [Ambient System](./system-ambient.md)；触摸它时会发生什么，见[彩蛋](./ambient-easter-eggs.md)；样式、选择器和图片，见 [Wallpapers](./wallpapers.md)。

同一地点、同一时刻（旧金山，22:30），两种天气预报：先是晴天，然后是中雨（WMO 63，3.2 mm/h，95 % 低云量）。星星消失是因为云层遮住了它们，而不是因为换上了一套"雨天"配色；雨丝随预报的风向倾斜。（无头浏览器手机尺寸，软件 WebGL，天气预报为模拟数据。）

- 分钟级精度：黎明逐渐变亮，太阳的光晕沿东 → 南 → 西移动，星星在 −6° 以下渐渐出现。时段变化时没有台阶。
- 天气预报从不让天空突变：每个值都平滑过渡到新的目标。
- 晴朗的夜晚和阴天的夜晚看起来不同，40 % 的云量和 95 % 也不同：场景来自测量值，而不是天气状况的名字。
- 在深色主题下，白天是一片深邃的天空，而不是一片蒙上遮罩的明亮天空。

## 原理

`deriveWeatherScene()`（`lib/scene.ts`）把天气 × 太阳 × 月亮 × 主题变成一个与渲染器无关的 `WeatherScene`（字段见[概览](./system-ambient.md#the-scene)）。有两套引擎画它，所以切换引擎改变的是精细程度，而不是氛围：

| 引擎 | 用在哪里 | 怎么画 |
|--------|-------|-----|
| **Sky**（`lib/wallpaper/`） | `sky` 样式，整页，WebGL2 可用时 | 一次全屏 fragment pass（`shader.ts`）：天空渐变 + 太阳光晕和日轮、闪烁的星星、作为受光球体着色的有相位的月亮、两层朝太阳方向受光的视差 fbm 云层、漂移的雾、随机闪电、雨丝、五个深度层的飘雪、主题遮罩、抖动。不用纹理。 |
| **Gradient**（`gradient.ts` + `gradient-stack.tsx`） | `gradient` 和 `classic` 样式；所有样式下的小组件卡片；没有 WebGL2 时 Sky 的降级方案 | 太阳光晕径向渐变 + 云层 wash + 由场景配色得出的天顶 → 地平线线性渐变，通过图层栈交叉淡化。`gradient.ts` 还保留着最初按天气状况划分的配色，供 Classic 和 devtool 的 40px 状况缩略图使用，那里各种状况必须保持可区分。 |

### 渲染器

`WallpaperRenderer`（`lib/wallpaper/renderer.ts`）通过 `setScene()` 拿到场景，并负责每一帧发生的所有事情：

- **每个场景都是一个目标。** 每个 uniform 以各自的时间常数平滑过渡（天空约 1.8 秒，云和降水约 2.5 秒），所以重新请求数据永远不会造成突变。
- **天体绘制位置的过渡要快得多**（太阳和月亮约 0.25 秒）。实时时钟每分钟只让它们移动屏幕的千分之一，所以只有当手在驱动时钟时（devtool 的滑块）才感觉得到这个过渡，而那时日轮应当感觉是黏在滑块上的。真正的跳变则改为滑行（[见下文](#跨越跳变时滑行)）。
- **漂移在 JS 里累积**，来自平滑后的风（`uCloudDrift`，以及下文的下落向量），所以风的变化是滑过去的，而不是让天空瞬移。
- **像素预算**，来自 `support.ts`：桌面 110 万像素（4 核或更少时 70 万），手机 48 万（32 万），帧耗时过长时进一步降低，达到帧率上限时再恢复。场景本身很柔和，所以 CSS 放大看不出来。两种配置的帧率上限都是 60，因为上限只能取刷新率的整除数（60 Hz 屏幕上的 45 实际是 30），所以像素是唯一的调节杆。"便宜到可以多给像素"指的是*达到*上限，而不是超过它：上限把 `dt` 卡在预算上。
- **云层覆盖为零时立刻跳过该层**（`cov <= 0.0`，不是一个阈值），所以任何带云的像素都不受影响，帧逐位相同。云层朝向太阳一侧的边缘采样是一帧里最贵的东西，否则晴朗的夜晚也得在每个像素上为它付费。
- 标签页隐藏时暂停，`prefers-reduced-motion` 下只渲染一帧静止画面（`setReducedMotion`），能挺过 context 丢失，并且只在第一帧画完之后才淡入 canvas（没有黑屏闪烁）。
- `<WeatherWallpaper />`（`components/wallpaper.tsx`）是 canvas 外壳；WebGL 失败会报告给 provider（`reportShaderFallback`），页面降级到 Gradient。

### 太阳和月亮

`lib/solar.ts` 根据访客的坐标计算太阳的**高度角和方位角**（NOAA 算法）。没有坐标时，它退回到一条由日出 / 日落（或本地时钟）估算出的弧线，所以第一次绘制也是对的。

**月亮**使用一套低精度的月球星历（Schlyter，约 1°）：站心高度角和方位角，加上由日月角距得出的月相。它在真实的时刻升起、过中天、落下，月相与日历一致（`getMoonPhaseName()` 给出八种月相名称）。明亮的高月会抬亮夜空和云顶，并冲淡暗弱的星星；云和雾会遮住它。在南半球，月牙是镜像的。没有坐标时，月亮就是太阳的估算弧线，按其月相所占一天的比例落后：新月时与太阳一同过中天；满月时在日落时升起。

**布景**（`lib/scene.ts` 中的 `stageSun` / `stageMoon`）。天体*在*哪里来自星历，从不扭曲；它*画*在哪里是一个构图决定：

- 垂直映射是一个舞台，而不是量角器：升起几度的月亮就已经画在页面内容上方的那条带里，然后从那里一直爬到紧贴顶边的位置。线性映射会让一整晚的月亮大部分时间都藏在小组件网格后面。
- 水平方向上，它随方位角由东向西穿过（南半球镜像），并避开最边缘，所以升起的月亮永远不会只露出半个。
- 白天的月亮只在升得足够高、且离太阳超过约 40° 时显示，是一个苍白的圆盘，强度不到夜间的五分之一。
- 靠近地平线时最多画大 30 %（月亮错觉）。

**画月亮。** 月轮和日轮一样大（`DISC_R`；在真实天空中两者都是半度宽）；让太阳看起来像太阳的是它的光晕。月亮是作为球体着色的，而不是用圆盘遮罩：月相变成一个光照方向，表面用 Lommel-Seeliger（让满月直到边缘都明亮的后向散射）加上一点 Lambert 和临边昏暗来照明，所以明暗界线是一段渐变。它的纹理（月海、高地、一片稀疏的环形山，其起伏会让法线倾斜）按弧角排布，所以越靠近边缘越被压缩，并随像素的覆盖面积淡出，所以没有任何东西会闪烁。全部是程序生成的。

### 天气往哪里落

这是模型的核心。处于终端速度的雨滴几乎立刻就会沿着重力与风的**合成**方向下落：穿过空气的速度不变，只是指向别处。所以对于下落的东西来说，风改变的是*哪边是下*，而陀螺仪移动的是重力本身。**倾斜和风是同一个表达式**，shader 永远只看到它们的和：

```
fall = g + perp(g) · lean
```

`g` 是页面空间中的单位重力（竖直或平放在桌上时为 `(0, −1)`，否则为传感器读数），`perp(g)` 是重力转过四分之一圈（`g` 指向屏幕下方时为屏幕右方）。倾斜改变 `g`；风设定 `lean`。两者只通过四个 uniform 影响天气，别无他途：

| Uniform | 是什么 |
|---|---|
| `uRainDown` | 雨的运动方向。雨丝*就是*雨滴的运动模糊，所以雨在与之对齐的坐标系里采样（`fallSpace()`，shader 里唯一的一次旋转）。 |
| `uRainFall` | 雨已经落了多远，以它自身行进的秒数计。倾斜的下落更长，所以阵风不仅让雨倾斜，还让它变快。 |
| `uSnowDown` | 雪的同一个方向，在同样的风下角度要平得多。飘动是横跨这个方向来测量的。 |
| `uSnowFall` | 雪行进了多远、沿着什么方向，是一个以秒为单位的向量。它也是风对雪的全部横向作用。累积前不做归一化（倾斜的下落更长）；每一小时回绕一次，因为再往后 float32 的小数位就不够了。 |

- **它是旋转而不是错切。** 错切在让雨滴倾斜的同时也会拉长它，所以一阵强风看起来像笔刷；旋转让雨滴倾斜而不改变它的形状。
- **倾斜是横跨重力的，而不是横跨页面的。** 风在世界中是水平的，也就是垂直于下落方向。把手机横过来，风暴也跟着你转，每一片雪花都保持与重力的夹角。如果改成沿页面方向，在 90° 时风就会顺着下落方向直直往下吹。
- **雪保留的是行程而不是时钟**，所以它的方向可以慢慢转过来，而已经在下落的雪花继续飘落，并弯向新的下方。因此雪在每个深度的倾斜自然是一致的。
- **一片雪花的位置从不取决于哪边是下。** 只有行程和每片雪花的飘动跟随重力；格子、行和长周期的飘荡都留在页面上，否则雪转向时整片雪场都会滑动。竖直时，这一帧与没有陀螺仪时的天空逐位相同。

每种东西以自己的速度响应，倾斜和风都一样（雪花无法知道是哪一个变了）：

| | 重新对准的方式 | 原因 |
|---|---|---|
| **雨** | 一次缓动，`RAIN_FALL_TAU` 0.08 秒 | 雨滴小、快，而且已经一路落到底，所以一眨眼就到了新的角度。缓动只是让一阵猛风不至于显得突兀断裂。 |
| **雪** | 一个临界阻尼弹簧，`SNOW_FALL_OMEGA` 0.9 rad/s | 缓动以全速离开，看起来像拖拽；弹簧从静止开始，看起来像有**质量**。临界阻尼：没有过冲。隐式积分：卡顿的一帧不会让它振荡。 |
| **云** | 只看天气预报 | 你不可能挥挥手就搅动一层云。 |

对一次 54° 的甩动并保持住，雨在 0.12 秒内到达 97 %；雪在 0.84 秒时到达 21 %，5 秒时到达 94 %，没有过冲。这个差距读起来就是重量感。

**风的符号。** Sky 里所有的水平量都是屏幕空间的，并且**正值向右**：`wind.x`、手划出的阵风、`uCloudDrift`、`uSnowFall`。`scene.ts` 把气象学的风映射到这上面：屏幕朝南看，所以西风（来自 270°）吹向东方，在北半球是屏幕*左*方，南半球镜像。在 shader 里，行程在使用处被**减去**，因为向右采样程序生成的场等于让它向左走；这个取反正是在遵守约定。风是奇对称的：不叠加任何恒定漂移（曾经有一个，导致微弱横风下雪和雨朝相反方向倾斜），而且雪的风从场景的风开始，而不是从零开始。

`wind.x` 是 `speed × sin(from) × hemisphere`，所以沿南北轴的风在任何风速下都不会产生倾斜。这就是为什么 devtool 的 Tune 折叠区有**两**行风的控件，`Wind` 和 `From`（`SceneOverrides.windSpeedKmh` / `windDirectionDeg`）。`From` 轨道的范围是 270° → 450°（从西经北到东），而不是 0° → 359°，因为在这半圈里倾斜是单调的：往左拖，雨就往左斜。每个偏南的方位画出来都和它偏北的镜像完全一样（`sin(180° − d) = sin(d)`），所以没有丢失任何东西。

### 陀螺仪倾斜

雨和雪沿着重力落下，而不是沿着视口的底边：把手机倾斜，雨丝也跟着倾斜；把手机横过来，雪就横着穿过页面。只有 Sky 有可以倾斜的雨滴；Gradient 和 Classic 会忽略它。

**陀螺仪是第二个重力，而不是一台相机。** 天空是装在页面里的一个世界：它的天顶是视口的顶部，太阳和月亮按星历给出的位置穿过它。倾斜告诉这个世界哪边是下，只有下落的东西会响应。另一种理解，即手机是一扇窗、视野反向旋转，是一个独立的功能：[天空之窗](./ambient-easter-eggs.md#the-sky-window-any-weather)。

`lib/gyroscope.ts` 把一次 `deviceorientation` 读数变成一个单位向量，表示页面坐标系中的下方（`gravityFromOrientation`）：

```
g_device = (cos β · sin γ, −sin β, −cos β · cos γ)     // Earth-down, in device axes
```

Alpha（指南针）被消去了：你面朝哪个方向，不会改变东西往哪里落。屏幕平面上的分量按 `screen.orientation.angle` 旋转，当手机平放得没有方向时，再混合回竖直。读数在传感器端做平滑（`SENSOR_TAU`，0.12 秒，以时钟为基准，因为事件以设备喜欢的任何频率到达）。它不是 React state：一个共享的 `deviceorientation` 监听器直接喂给 `WallpaperRenderer.setGravity()`。在减少动态效果下，两个下方都直接跳到读数。

**访问权限。** 所有带传感器的浏览器都会自由触发这个事件，只有 WebKit 例外，它把事件挡在 `DeviceOrientationEvent.requestPermission()` 和一次用户手势之后：

| | 行为 |
|---|---|
| Chrome / Firefox / Android | 加载时直接遵从保存的意愿（`weatherGyro`，默认开启）。 |
| iOS / iPadOS | 意愿要等一次点击：选择器 Weather 标签页里的 **Tilt** 一行、devtool 的 Sky → Gyro 一行、下文的倾斜引导，或天空之窗的邀请。打开它*就是*发起请求的那个手势。 |
| 之前授权过 | `weatherGyroGranted` 记下这一点，下次加载时静默重新获取权限。这条记录是唯一会在没有手势时调用 `requestPermission()` 的原因。 |
| 没有传感器（桌面） | 所有桌面浏览器都定义了 `DeviceOrientationEvent`，但没有一个会触发它，所以 provider 会等第一次读数，Tilt 一行显示 *no motion readings*（`gyro.readings === "silent"`）。 |

### 倾斜引导

选择器里的开关离页面有三次点击之远，而它提供的是访客从未见过的东西。所以**在下雨或下雪的 Sky 上，把手指按在首页背景上，会弹出倾斜功能的说明，下方有一个按钮发起请求**（`TiltPrimerSheet`，`lib/tilt-primer.ts`）。第一次按下换来说明；第二次才用掉那唯一的机会，因为被拒绝的权限在哪里都是终局的。

- **由画面来解释**：一部手机来回摇摆，里面的雨朝反方向摆动。镜头跟着设备转一部分（手机画在 0.45·θ，雨在 −0.55·θ，θ = 24°），所以因和果都在动。它是 CSS 而不是 JS：两个时长相同的声明式动画，不会因为主线程繁忙而逐渐错开。减少动态效果时它们停在 0%。
- **它会留着告诉你结果**，因为光看天空说不清楚：已授权（1.4 秒，继续摇摆）、被拒绝（3.0 秒，手机竖直、雨直直落下，并说明去哪里撤销），或者两者都不是（WebKit 没弹对话框就拒绝了；按钮会回来）。这就是 `setGyroEnabled` 会把权限结果交回来的原因。
- **只邀请一次。** sheet 一被响应，`weatherGyroPrimed` 就被写入（通过 `setTiltPrimed`），在发起请求之前，关闭或滑走也算。`shouldOfferTilt` 在以下每种情况下都保持安静：机会已用掉、没什么可请求的（不是 WebKit，或已经被拒绝）、在选择器里关掉了倾斜、没有东西在下落，或者 Sky 没有在绘制。
- **只在系统界面上。** 按压必须落在 `.system-surface` 里（首页，它是一幅构图而不是一篇文档；见 [Four voices](./design-system.md#four-voices-chrome-surface-voice-document)）。壁纸在每个路由上都是整页的，而在文章上，长按属于读者。
- **要求静止，这样它就永远不会和同一背景上的阵风冲突**：按住 400 毫秒（`TOUCH_HOLD_MS`）不动才是邀请；在那之前的任何移动都属于阵风或滚动，此时它就退让。它从不调用 `preventDefault`。
- **它叠在 iOS 自己的按压之上。** WebKit 约 500 毫秒的 callout 计时会在 400 毫秒按住之上触发 `pointercancel`，所以整个按压期间都抑制 `-webkit-touch-callout`（`lib/poke.ts` 中的 `holdCallout()`，与擦雾共用），是保存再恢复，而不是清除。Chromium 的 CSSOM 会静默丢掉这个属性，所以无头测试只能监视 `setProperty`。

sheet 是从一个 `setTimeout` 里打开的，那不是手势；sheet 里的按钮才是，它在同一个任务里调用到 `requestPermission()`。

### 跨越跳变时滑行

缓动是给漂移用的。**跳变**（相隔一座城市的一次定位、休眠数小时后的一次重新请求、devtool 时钟上的一个预设）会在 `GLIDE_SEC`（0.9 秒，ease-in-out）内滑行过去：插值的是天体**在世界中的方向**，沿球面走短的那条路，每一帧都经由 `stageSun` / `stageMoon` 布景（或通过天空之窗投影）。日轮沿弧线越过，而不是沿直线滑过玻璃，太阳从不那样移动。滑行是在一个目标和下一个目标之间度量的，而不是相对于日轮已缓动到的位置，所以拖动滑块永远不会让它重新开始。

天空之窗的镜头在一次更新中视角跳变超过 `VIEW_JUMP_DEG`（20°）时也这样做：在 `VIEW_GLIDE_SEC`（0.6 秒）内做一次四元数 slerp（`slerpView`）。星空球缓动它的纬度和恒星时角。停止的渲染器会让每次滑行直接到位；减少动态效果下永远不会开始滑行。

### 稳定（转圈指示）

日常的变化保持安静：太阳的漂移、返回同一座城市的一次轮询。当天空要花一秒从一个状态过渡到另一个状态时，右上角会出现一个小圆环（`<SettleSpinner />`），由 `lib/settle.ts` 提供：每个来源在稳定期间持有一个具名原因。

| 原因 | 持续期间 |
|---|---|
| `sky` | 整页渲染器正在进行一次滑行（太阳、月亮或镜头） |
| `compass` | 天空之窗在等待第一次读数（最多 1.5 秒），或 WebKit 的指南针偏移正在校正超过 6°（直到在 2° 以内） |
| `location` | 一次请求的定位正在进行中；以及位置移动超过 `SETTLE_MOVE_KM`（30 km）之后的 `SETTLE_EASE_MS`（2.6 秒） |
| `weather` | 正在请求新位置的天气预报，之后在它铺开时持续 2.6 秒；以及预报让天气状况或云量变化超过 30 个点之后的 2.6 秒 |

它在 150 毫秒（`SHOW_AFTER_MS`）后出现，并保持 700 毫秒（`HOLD_MS`），所以瞬间就稳定的变化永远不会让它闪一下，而两个接连出现的原因看起来就像一个。它不接收指针事件，以 `--ink` 画在壁纸上，在减少动态效果下是静止的。

### 渐变交叉淡化

场景变化时，CSS 渐变必须渐变过去，而不是突变。provider 维护一个**图层栈**（`layers`）：每次变化压入一层，共享的 `<GradientStack />` 在 `crossfadeMs` 内把最新一层淡入到下面那层之上，然后 provider 修剪到只剩最新的。一个渲染器同时服务整页 wash 和每个小组件的叠层，所以它们的过渡完全一致。iOS 的 `fixedBgTracker`（`lib/fixed-bg-tracker.ts`：一个 background-attachment polyfill 加上一个相对视口的边缘 mask）按图层应用，所以柔边在交叉淡化中途也保持不变。

### 天空与主题

太阳决定天空里有什么；主题决定它有多亮。Light 下的白天和 Dark 下的夜晚，两者一致，遮罩就够了。其他组合正是遮罩失效的地方：混向页面颜色之后，Dark 下的正午天空变成灰蓝色的中间调，Light 下的夜晚变成石板色。

**基调。** 所以 `deriveWeatherScene()` 会给天空重新定调，就像 Apple 的浅色/深色壁纸对那样：每种天空和云的颜色的 OKLab 明度被移入主题的范围，色相保持不变（`lib/scene.ts` 中的 `THEME_KEY`）。

| | 变成什么 |
|---|---|
| 深色主题，白天 | 正午的天空被压进深色范围：深蓝色，云仍比天空亮，日轮保持明亮，光晕定调一半。蓝调时刻，持续一整个下午。 |
| 浅色主题，夜晚 | 夜晚被抬进浅色范围：淡淡的月光薰衣草色，较亮的星星仍然可见，月亮被调暗成白天的月亮，以免看起来像太阳。 |

定调的程度随太阳高度角变化，并且**在两侧的暮光期间都为零**（Dark 是地平线到 14°，Light 是 −2° 到 −10°），而这正是 Follow the Sun 下主题交接的地方，所以交接时永远不需要和基调较劲。下游的一切都在不知情的情况下读取定调后的场景：shader、Gradient、小组件卡片、`profileFromScene`、devtool 的日程条。Classic 不定调：它的表是为白天/夜晚 × 浅色/深色这四种情况全部手调的。主题变化时，Sky 定调后的颜色（`renderer.ts` 中的 `keyed`）按主题的时钟缓动（`setThemeEase`），而不是按自己的 1.8 秒，所以天空和 chrome 同时到位。

**暮光外观。** 基调在越过地平线时为零，日落时主题剩下的就只有遮罩和曝光，所以在那里切换主题会把一个明亮的乳白色日落变暗。所以**暮光不属于任何一个主题**（`lib/scene.ts` 中的 `TWILIGHT_LOOK`）：越接近太阳越过地平线的时刻，两种外观都被拉向同一个（无遮罩，曝光 0.8），越过期间两者完全相同，逐位一致。

```
           light's own   ←──── meet ────→   dark's own
  light  ──────┬────────────┬────┬───┬───────────────────────
             +12°          0°  −1.5 −4
  dark   ──────────────┬────┬────┬──────────────┬────────────
                      +4    0°  −1.5           −8°
```

- **平台区**（−1.5° 到 0°）覆盖交接真正落下的地方：预报给出的日出和日落、星历上的 −0.83°、估算弧线上的 0°。它在深色基调开始的地方结束。
- **越过之后**，只有手动选择的主题才会到达那里，每种主题在几度之内收回自己的外观，在基调到来之前。
- **在哪里汇合**是一个可读性决定：大约在浅色卡片和深色卡片的色调冲突相等的画面明度处（`lib/legibility.ts` 中的 `toneSafe`：Light 希望画面高于 0.62，Dark 希望低于 0.45）。晴朗的日落落在 0.53 附近。

两种外观按它们画出的结果混合（`gain·col + offset`），所以中间的每一帧都是两者的简单混合。Gradient 用同样的权重，以共享的曝光替换自己的遮罩提亮（`CSS_VEIL_BOOST`），`profileFromScene` 也用同样的曝光来测量。两者都从场景读取它（`flat`），所以都不必知道暮光的存在；离开暮光时它就是 1 和 1。交接本身（chrome 何时切换）见[主题跟随太阳](./system-ambient.md#the-theme-follows-the-sun)。

## 约束

| 约束 | 原因 | 打破之后 |
|---|---|---|
| 所有的风和倾斜只通过 `uRainDown` / `uRainFall` / `uSnowDown` / `uSnowFall` 影响天气 | 两者共用一个模型，天空永远不会有两套物理 | 雪和雨不一致；阵风和倾斜让雪花以不同的速率移动 |
| 雪里任何与位置有关的东西都不跟随重力 | 只有行程会转向 | 手机转动时整片雪场滑过页面 |
| 水平方向是屏幕空间、正值向右；行程在采样处被减去 | 气象学的风只在 `scene.ts` 映射一次 | 天空逆着指南针倒着吹（曾经确实如此，一直没人发现，直到手划出的阵风暴露了它） |
| 天体的世界位置从不扭曲；只有 `stageSun` / `stageMoon` 安排它的位置 | 星历是事实，布景是构图 | 对这个日期和地点来说，月亮出现在天空中错误的位置 |
| 减少动态效果：一帧静止画面，不滑行，下方直接跳到读数 | 这个设置关乎运动 | 一个明确不要动画的偏好设置背后还在动画 |
| `cov <= 0.0` 保持为精确判断 | 逐位相同的帧，就是这样验证的 | 阈值会改变带云的像素 |
| 陀螺仪读数不进入 React | 每秒约 60 个事件，没有任何东西依据它们渲染 | 每个传感器事件都触发一次渲染 |

## 做法

**不用等就看到某种天气。** Devtool → Sky 模块。六个天气状况标签可以强制其中一种（再点一次回到真实天气）；时间轴的播放头和时段名称会移动生效时钟（`timeScrubMinutes`），日期一行会移动日期（`dayOffset`，会移动月亮）。**Tune** 折叠区里有作用于推导出的场景的滑块：Cloud、Precip、Wind、From、Veil。**Now** 会把这些全部重置。强制某种状况时画出的正是它的 profile；测量值只会来自真实的天气预报。

**检查一次 shader 改动。** 标准是"该逐位相同的地方逐位相同"：`uWindow = 0` 时天空之窗的代码、云层跳过、竖直时的陀螺仪。把旧的和新的 shader 并排编译，用同样的 uniform 比较帧。

**没有 WebGL2 时。** Devtool → Wallpaper → **No WebGL2**（`noWebGL` 覆盖）会强制降级到 Gradient；选择器的 Sky 图块会显示那条说明。
