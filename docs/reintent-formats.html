Reintent 格式谱系

同一个意图（他帽子有多大），从草稿到现在被写成了七种样子。这里逐个列出每一次换格式得到了什么、丢了什么，找出来回摆动的原因，再从谁写什么、多久改一次出发，重新划一遍 Core 与 userland 的边界。

一 · 谱系

每一版，同一个帽子

顺序就是实际的先后。绿色是往前走，黄色是后来被撤回的绕路。

F0

草稿 Re-intent-ify

起点

意图是 sum type；模型 infer，人 resolve；概率与「拿不准就问」；eager / lazy 两种求值；给了 Signal 和 React 两种写法，没有选。

// The React way
function Layout() {
  const intent = useIntent<Layout>("unresolved")
  switch (intent.kind) { case "pin": … case "flow": … }
}
// The Signal way
const layout = intent<Layout>("unresolved"); layout.infer(ctx); react(() => …); layout.resolve("row")

立下的

  • 意图是输入，计算对意图做出反应
  • 概率 + 人在环里：选项少、模型挑、拿不准就问
  • 传统计算是更低一层的实现细节

悬而未决

  • Signal 还是 React
  • 树还是图
  • 意图从哪来、身份是什么
F1

数据树

packages/intents · #504 前后起点实现

场景的意图树是一份 JSON：节点、每个节点上的意图、每个 kind 在画面里是什么（realize）、模型的判断、视图路径、原文片段。

nodes: [{ id: "man", aka: ["他"], intents: {
  hat: { kinds: { usual: { realize: { hatScale: 1 } }, big: …, absurd: … },
         p: { usual: .04, big: .52, absurd: .44 }, resolve: "ask", view: ["man.hat"] } } }]
spans: bindWords(PROMPT, [["大很多", "man", "hat", "big"], …])

得到

  • 模型能整份读写（纯数据）
  • 原文片段 ↔ 树的绑定（spans）
  • 手势 ↔ 意图的绑定（gesture）
  • 视图只读数据

缺

  • 不能表达意图之间的关系（条件、守卫、默认跟随）
  • 没有类型
  • kind、画面数据、判断混在一处
F2

JSX 声明

3f36161加了类型

同一棵数据树改用 TSX 写，toProgram 求值成数据；kind 搬到 .ts 的 intent()，有了类型。

<Scene id="wardrobe">
  <Thing id="man" aka={["他"]}>
    <Intent name="hat" of={Size} p={{ usual: .04, big: .52, absurd: .44 }} resolve="ask" view={["man.hat"]} />
  </Thing>
</Scene>

得到

  • 类型检查（kind 来自 Size）
  • JSX 嵌套就是树
  • derive、作者预选、观看者倾向（decide.ts）
  • root、effect、devtools

丢了

  • 原文片段绑定（只剩 prompt 字符串）
  • 手势绑定
  • 本质问题：意图是 JSX 的输出，你指出它应该是输入
F3

Parts：意图进，画面出

db44210意图变成读视图混进来

意图改成在函数里读（useIntent），这是对的一步。但每个 part 同时把画面画出来，意图层和视图层合成了一层。

export const Man = part("man", { aka: ["他"] }, (pose) => {
  const hat = useIntent("hat", Size, { p: { … }, resolve: "ask" });
  return <Figure hatScale={hat.data.hatScale} … />;   // the drawing, here
});

得到

  • 意图是输入
  • 关系就是代码：守卫是分支，默认值可以算
  • 读在 if 下也可以（按名字认）

丢了

  • 纯语义层：模型想改意图就得写画法
  • 显式的树（只剩 part 列表）
  • 宿主中立
  • 判断 p 写死在代码里
F4

React 状态库（方案 C）

de48c9c绕路

真正的 React hook，render 时读、commit 时声明（root.hold），每格单独订阅。意图树变成了 React 的挂载树。

<ReintentRoot root={root}>
  <Thing id="man"><ManFigure /></Thing>   // useIntent: a React hook inside
</ReintentRoot>
// render reads · commit declares · per-cell useSyncExternalStore

得到

  • 能直接接进真实的 React 应用
  • 细粒度更新

丢了

  • 模型看得见的程序（树只存在于挂载之后）
  • 便宜的反事实：要看另一种可能就得再挂载一次
  • 两种 hook、hook 规则、300 行的 root
  • 又往 signal 订阅那边走了
F5

值语义，三层

d2d84e7 · 移植 airtalk#845往前

树回来了，但这次是主体的树（梦、他、衣柜），不是意图的树；意图是树上节点里的读。判断从程序里搬到 source，按路径存。

// program/v1.tsx: what the model writes, literals only
<Dream key="wardrobe"><Man key="man" /><Wardrobe key="wardrobe" /></Dream>
// intents/v1.ts: semantics, no view
function Man() { const hat = Size.read("hat", { default: "big", ask: true }); return host("man", { hat: ref(hat) }) }
// beliefs.ts: the source, by path
"Dream:wardrobe/Man:man#hat": { usual: .04, big: .52, absurd: .44 }

得到

  • 纯语义层，模型能读写的字面量实例树
  • 渲染是纯函数：whatIf、备选、该不该问都只是再调一次
  • 身份是路径（key + scope），改写后不丢
  • kind 没了，决定就等着，不改数据
  • 和 airtalk 同一个核心

丢了

  • derive、作者预选、观看者倾向（改成算出来的默认值）
  • 判断与程序同处一地；现在是手写路径字符串，没有类型
  • 模型写一份文件变成写三份
  • 视图那边要手写 meaningOf 把节点翻回画面
F6

选择与世界

09710ad往前

判断可以以前面读到的值为条件（Given）；<Choose> 在子树之间选；worlds 先整组选一个世界再渲染。

<Choose key="ending" name="ending" default="waits"
  alternatives={{ waits: [<Man key="man" />, <Wardrobe key="wardrobe" />], gone: <Wardrobe key="wardrobe" /> }} />
"…#door": { $given: [{ when: { "…#ending": "gone" }, p: { ajar: .8, … } }] }

得到

  • 相关的选择不再拼出不一致的组合
  • 结构本身可以拿不准
  • 按世界问人，问得更少

代价

  • 判断格式更复杂，条件只能指向更早读到的意图
  • worlds 要手动指定 only
  • 条件判断还没有真模型验证

三 · 为什么来回摆

七条轴，三条在摆

把「格式」拆开看，每一版其实是在七条轴上各选了一个位置。四条轴是单调往前走的；来回摆的只有三条（黄色）。

树是什么的树主体 + 意图主体 + 意图没有显式的树React 挂载树主体的树

真正往前的只有两步。F2 → F3：意图从输出变成读。F4 → F5：值而不是订阅，加上三层分离。

两步是绕路，都已被撤回。F3 把视图混进意图层，F4 把程序交给 React 的运行时。两次都是为了让一个例子（衣柜的画面）少写点胶水，牺牲了 R1、R4、R7。

根因：我们一直把五种东西当成一个「格式」来设计：kind 的词汇、语义代码、实例树、判断、视图。它们的作者不同，改动频率也差几个数量级。每次为一处的痛点挪了边界，就把另一处带着一起挪。三条在摆的轴（树、判断、视图）正好是这几样东西的边界。

四 · 第一性

按「谁写、多久改一次」切

一样东西放在哪，由写它的人和它的改动频率决定，不由哪个例子写起来顺手决定。

东西谁写多久改一次形式在哪一层
词汇：kind、词、每个 kind 的数据工程师；模型学到新 kind很少，只增不改.ts 数据userland（vocab）
意图组件：读什么、怎么分支、说出什么工程师；模型偶尔改写每个程序版本代码userland（领域组件库）
实例树：这一个梦、这一份 deck 由哪些主体组成模型每个实例字面量 JSX程序
判断：模型对每个意图的分布模型每次推断，很频繁按路径的数据source
决定：人说了什么人每次交互按路径的数据source
视图：画面、版式求解宿主工程师每个宿主任意代码host

Core 就是把它们连起来的那一个函数：render(实例树, source) → (host 树, trace)，组件按名字读 source。一个特性放进 Core，当且仅当它改变这个函数对同一份输入算出的结果，而且不能只用公开 API 写出来。两条都满足才进 Core，否则进 userland。

草稿里的 sum type 带字段（{ kind: "row", alignment: AlignmentIntent }）也落在这条线上：一个带字段的分支，等于「一个选择，加上只在这个分支下才读的意图」。v2 里只在不站在窗边时才读目光，就是这个。JSX 嵌套就是那个 bind，Core 不需要 ADT 类型。

五 · 边界提案

最小 Core，和 userland 的组件

拿上面的判据逐个过一遍现有的 API。

Core（7 个概念）

  1. jsx / h、Fragment、host(kind, props)：元素。对应 createElement
  2. key + scope(C)：身份就是路径
  3. createContext（带数值轴）、useCtx
  4. useIntent(name, { default, kinds, open, ask }) → 值、Unresolved 或 Unknown。唯一的选择原语，对应只读的 useState
  5. render(el, source, { provide, overrides }) → { tree, trace }。whatIf 只是 overrides 的别名
  6. Source 约定（get、deck、unknown、subscribe）和一个参考实现
  7. 定值规则，以数据格式给出：写者优先级与 TAU、$not、Piecewise、Given、kind 约束与 waiting、学到的 kind

Userland

  1. 领域组件：Man、Wardrobe；airtalk 的 Row、Stack 等
  2. 结构组件：Choose（30 行，只用 useIntent + host，证明它不属于 Core）
  3. 求值策略：worlds / split、alternatives、questions、orphans
  4. 语言：vocab、words、observe
  5. 宿主循环：session（历史、撤销、版本、Model 接口）、changes
  6. 降级候选：watch（subscribe + render 就能写）、createCache / under / stale（只读 trace）
ReactReintent Core不同在哪
createElement / JSXjsx、hosthost 节点对 Core 没有意义，只对宿主有
keykey + scope → 路径路径要存下来，要跨改写存活；所以组件名用 displayName
useStateuseIntent渲染里只读，写发生在外面（source）；有不确定的值
reconciler定值规则比的不是旧树和新树，是几个写者谁说了算
ContextContext + 轴轴让一个决定可以按屏幕比例之类分段
renderer（react-dom）host（React 视图、版式求解）同
concurrent / transitionsoverrides（whatIf）多个世界同时渲染，互不干扰

六 · 还没收回的

一路上丢掉、至今没补的

  • 原文片段 ↔ 树（F1 的 spans）：哪一段原话说的是哪个意图。自然语言绑定只剩词表。
  • 手势 ↔ 意图（F1 的 gesture）：拖动到哪个 kind。
  • 视图路径（F1、F2 的 view）：Inspect 用它高亮。现在只能由宿主自己映射。
  • 观看者倾向、作者预选（F2 到 F4）：现在只有人、整份的规则、模型、代码四个写者。
  • 判断与程序同处一地、有类型（F1 到 F4）：现在 beliefs.ts 里是手写的路径字符串，写错了不会报错。
  • 模型只写一份文件（F2）：现在是实例树、意图组件、判断三份。
七 · 一起定

要决定的六件事

每一件都标了我的倾向。定下来之后，换格式要守一条规矩：至少让一条需求从 ✗ 变 ✓，并且没有一条从 ✓ 掉下来。做不到就是绕路，不改。

Q1模型写什么？

只写实例树和判断，意图组件由工程师提供的库给；还是也写（改写）意图组件？这决定 userland 组件库的边界和 R1 的成本。

倾向：默认只写实例树 + 判断；改写组件是少数情况，走程序版本。

Q2判断能不能写回树上？

例如 <Man key="man" p={{ hat: {…} }} />，由 lib 在加载时搬进 source。能收回局部性和路径检查，Core 不用动。

倾向：可以，作为 userland 的写法；source 仍是唯一的状态。

Q3Choose 留在 userland？

它只用公开 API 就写出来了。进 Core 唯一的理由是让静态分析认得它。

倾向：留在 userland。

Q4watch、whatIf、缓存降级？

三个都能在 Core 之外写出来。降级后 Core 只剩 render 一个求值入口。

倾向：降级；whatIf 保留为 overrides 的别名。

Q5原文片段绑定放哪？

作为实例树上的字面量 prop（随树改写），还是作为 source 里的数据（随推断更新）？

倾向：实例树上，它和树一起被模型写出来。

Q6Given 依赖读的顺序，能接受吗？

现在条件只能指向更早读到的意图，兄弟的先后有了意义。另一种做法是按路径声明依赖、两遍渲染，不受顺序影响，但更贵。

倾向：接受顺序；它就是 bind 的顺序，和 JSX 嵌套一致。
